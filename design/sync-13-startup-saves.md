# 후속 13번 — 시작 동기화 도중 바뀐 저장 목록(sl_saves)을 덮어쓰는 문제: 수정 설계

> 설계 문서. 앱 코드(index.html · js/ · css/)는 바꾸지 않는다. 사용자가 이 설계를 승인한 뒤에 고친다.
> 기준: `main` a638f7d (2026-10-18) · `cloud.js?v=32`
> 관련: PR #170 (재현 테스트, `tests/zz-cloud-save.test.js` "알려진 문제 · 후속 13번") · PR #169 (`design/sync-11-cloudsave.md` 4절 2번)

## 0. 결론 먼저

- **원인:** `js/cloud.js` `_startupSync` 는 시작할 때 읽은 `sl_saves` 를 쓴다(`cloud.js:506`). 네트워크 왕복 4~5번 뒤, 내려받은 경기를 넣거나 중복을 정리한 결과를 그 **읽어 둔 값 그대로** 다시 쓴다(`cloud.js:588`). 그 사이 이 기기에서 목록을 바꾼 것은 모두 덮인다.
- **확인된 것 (PR #170):** 동기화 도중 저장한 새 경기의 목록 항목이 빠진다. 데이터 키는 남는다.
- **같은 원인으로 예상되는 것 (코드 읽기로만, 고칠 때 테스트로 먼저 확인):**
  - 동기화 도중 이름 바꾸기 → 옛 이름으로 돌아간다.
  - 동기화 도중 삭제 → 목록 항목이 되살아난다. 서버 응답에 그 행이 실려 오면 데이터까지 되살아난다.
- **추천: 방향 A.** 내려받기 응답을 받은 직후 `sl_saves` 를 **다시 읽고**, 동기화 도중 목록에서 사라진 키는 내려받지 않는다. 그 아래부터 쓰기(588)까지는 모두 동기 실행이므로 끼어들 틈이 없어진다. 팀 코드 동기화(`core.js:9990` `saves2`)가 이미 이렇게 한다. `cloud.js` 만 약 8줄 바뀌고, `?v=` 는 `cloud.js` 하나만 올린다.
- 같은 모양(읽어 둔 `sl_saves` 를 비동기 뒤에 다시 쓰는 곳)은 **이 한 곳뿐이다.** `core.js` 의 `sl_saves` 쓰기 14곳은 모두 같은 동기 블록 안에서 새로 읽고 바로 쓴다(2절).

0단계와 4단계 사이에는 비동기 단계(1·2)가 있고, 3단계는 동기 실행이다. 1·2 동안 생긴 목록 변경은 4단계에서 덮인다. 덮이는 경우는 `added || cleaned` 일 때뿐이다. 그래서 새 기기에서 처음 로그인할 때나, 다른 기기에서 경기가 늘어난 뒤 로그인할 때, 또는 같은 경기 정리가 처음 돌 때 생긴다.

| 1·2 동안 사용자가 한 일 | 그 일이 쓰는 것 | 4단계 뒤 |
|---|---|---|
| 새 경기 저장 (`saveGame` 등) | 항목 추가 + 데이터 | **항목이 빠진다(재현됨, #170).** 데이터는 남아 목록에서만 안 보인다. 서버에는 저장 업로드(`cloudSave` 3초 타이머)로 올라간다 |
| 이름 바꾸기 (`renameGame`) | 항목의 label | (예상) 옛 이름으로 돌아간다 |
| 삭제 (`deleteGame`) | 항목 제거 + 데이터 제거 + `sl_cloud_del` | (예상) 항목이 되살아난다. 2단계 응답이 서버 삭제보다 먼저 만들어졌으면 그 행이 실려 와서, 로컬 데이터가 없으니(`!loc`) 데이터까지 다시 쓴다. 서버 삭제가 끝나면 `sl_cloud_del` 이 비워지므로 다음 동기화가 이 경기를 다시 지울 근거도 없다 |
| 가져오기 · 공유 경기 저장 · 자동저장 복구 | 항목 추가 | (예상) 저장과 같다 |

- 틈이 생기는 원인(낡은 목록)을 3단계 판단부터 없앤다. 저장 · 이름 · 삭제 세 경우를 한 번에 다룬다.

- `pend` 는 그대로 둔다. 0단계 삭제 대기의 서버 삭제가 실패한 경기는 지금처럼 내려받지 않는다.
- `pendNow`: 동기화 도중 지웠고 서버 삭제가 아직 안 끝난 경기를 거른다.
- `gone`: 동기화 도중 지웠고 서버 삭제까지 끝나 삭제 대기에서도 빠진 경기를 거른다. 2단계 응답에 그 행이 실려 와도 내려받지 않는다.
- `saves` · `entryOf` 는 클로저 변수라 다시 대입하면 된다. 1단계(업로드 고르기)는 0단계 목록을 그대로 쓴다. 도중에 저장한 경기는 자기 `cloudSave` 타이머가 올리므로 영향이 없다(#169 4절 3번).
- `JSON.parse` 가 실패하는 경우(깨진 `sl_saves`)는 0단계와 같아서, 바깥 `catch` 가 동기화 실패로 알린다.

## 4. 테스트 계획 (tests/, fail-closed · 실서버 금지)
